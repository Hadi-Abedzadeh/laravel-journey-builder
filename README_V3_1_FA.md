# Journey Builder v3.1 — راهنمای تغییرات و نصب در datasyncer

این بسته براساس سورس v3 قبلی ساخته شده و قابل انتشار به‌عنوان نسخه جدید Composer است؛ اتصال به SQL Server عملیاتی و سرویس SMS/API در این محیط تست نشده است. از ابتدا روی Staging نصب و آزمون کنید.

## تغییرات نسخه

- فهرست جرنی‌ها: حذف ستون‌های «کد داخلی»، «پیامک موفق» و «API موفق». کد داخلی فقط در سمت سرور باقی می‌ماند؛ در صفحه ویرایش و جزئیات هم نشان داده نمی‌شود. برای الگوهای HTTP API قبلی، placeholder سیستم‌داخلی `{{flowCode}}` همچنان کار می‌کند.
- نام منوی طراح به «ویرایش جرنی» تغییر یافته و ابزار Drag & Drop حفظ شده است.
- در جدول جزئیات اجرای جرنی، برای `failed` دکمه تلاش مجدد افزوده شده. برای SMS و API کاربر باید خطر ارسال تکراری را صریحاً تأیید کند. دکمه فقط وضعیت Run را به `ready` می‌برد؛ دستور `journey-builder:tick` بعداً همان گره ذخیره‌شده را اجرا می‌کند.
- خطای صریح HTTP در SMS/API دیگر باعث عبور از گره به شاخه failure نمی‌شود: Run در همان گره با `failed` متوقف می‌شود. خطاهای `unknown` یا `sending` به‌منظور جلوگیری از ارسال دوباره مسدود می‌مانند تا سمت سرویس مقصد تعیین تکلیف شوند. خطاهای HTTP الزاماً اثبات عدم دریافت توسط مقصد نیستند.
- پاک‌سازی اختیاری/قابل فعال‌سازی پس از خروج: Run و Step/SMS/API/Retry Logs مربوط به Run از دیتابیس حذف می‌شوند؛ شمارنده تجمیعی برای فلو و گره حفظ می‌شود و هش HMAC شناسه کاربر برای جلوگیری از ورود تکراری نگهداری می‌شود. این هش یک کلید (row) کوچک برای هر کاربرِ واردشده باقی می‌گذارد؛ پاک‌سازی به معنای صفر شدن تمام رکوردهای مرتبط با کاربران نیست.

## قبل از نصب

1. از SQL Server و فایل‌های پروژه پشتیبان بگیرید. موتور جرنی را در Staging آزمایش کنید و تا پایان تست پردازش Scheduler و ارسال خارجی را موقتاً متوقف نگه دارید.
2. به ریشه بسته مراجعه و `composer.json` را بررسی کنید؛ نام بسته باید `hadiabedzadeh/laravel-journey-builder` باشد. در Repository رسمی خود Commit/Push کنید و ترجیحاً یک tag پیش‌انتشار جدید بسازید. برای شاخه dev-main بعد از Push، در پروژه میزبان `composer update hadiabedzadeh/laravel-journey-builder` را اجرا کنید.
3. Migration جدید فقط سه جدول می‌سازد و قبلی‌ها را تغییر یا حذف نمی‌کند. بعد از به‌روزرسانی پکیج، مسیر Migration نصب‌شده:

   `vendor/hadiabedzadeh/laravel-journey-builder/database/migrations/2026_11_08_100000_add_journey_builder_retention_tables.php`

   برای اجرای فقط همین Migration (بدون تحریک Migration قدیمی jobs):

   `php artisan migrate --database=sqlsrv --path=vendor/hadiabedzadeh/laravel-journey-builder/database/migrations/2026_11_08_100000_add_journey_builder_retention_tables.php`

4. تنظیمات پکیج را دوباره منتشر کنید یا به‌صورت دستی کلیدهای جدید زیر را به فایل `config/journey_builder.php` اضافه کنید. **اگر config قدیمی منتشر کرده‌اید، mergeConfigFrom کلیدهای جدید در سطح root ممکن است با تنظیمات قدیمی overwrite شود؛ config منتشرشده را حتماً تطبیق دهید.**
5. دو متغیر زیر را در `.env` بگذارید؛ **کلید ثابت طولانی تولید کنید، آن را داخل Git قرار ندهید و بعد از اجرای پردازش تغییرش ندهید:**

   `JOURNEY_BUILDER_ENROLLMENT_HASH_KEY=<random secret 32+ characters>`

   `JOURNEY_BUILDER_PURGE_ON_EXIT=true`

   برای بررسی اولیه، اول `PURGE_ON_EXIT=false` و سپس پس از تست آن را `true` کنید. حذف اطلاعات خروج‌یافته برگشت‌پذیر نیست.

6. `php artisan optimize:clear` و `php artisan vendor:publish --tag=journey-builder-assets --force` را اجرا کنید. فونت Vazirmatn به‌علت حقوق فایل فونت داخل این بسته مجدداً قرار نگرفته؛ اگر فونت را خودتان در اختیار دارید، آن را با همان نام `vazirmatn-fanum.woff2` در `public/vendor/journey-builder/` یا در منابع Assets مخزن خود قرار دهید.

## فرمان‌ها

- `php artisan journey-builder:status --flow=3`: وضعیت جرنی و آمار کل (شامل خروج‌های پاک‌شده)
- `php artisan journey-builder:retry --flow=3`: فقط پیش‌نمایش قابلیت Retry، بدون تغییر دیتابیس
- `php artisan journey-builder:retry --run=123 --retry-external --ack-duplicate-risk --commit`: اجرای مجدد SMS یا API ناموفق **از همان گره**. رویداد توسط Tick پردازش می‌شود. فقط پس از بررسی وضعیت ارسال در سرویس مقصد.
- `php artisan journey-builder:prune --flow=3 --batch=200`: تعداد خروج‌های آماده پاک‌سازی، بدون حذف
- `php artisan journey-builder:prune --flow=3 --batch=200 --commit`: پاک‌سازی خروج‌های قدیمی؛ آمار را جمع می‌کند، هش نگه می‌دارد و جزئیات را حذف می‌کند. قابل بازگشت نیست.

## نکات سازگاری

- داده‌های `jb_runs` قدیمیِ فعال/درانتظار/ناموفق دست نخورده باقی می‌مانند. پاک‌سازی فقط `exited` را پردازش می‌کند؛ اطلاعات failed و unknown حذف نمی‌شود.
- اگر قبل از این نسخه، خطای ارسال موجب انتقال به شاخه failure و سپس exit شده باشد، رکورد آن خطا ممکن است دیگر در همان گره نباشد و با Retry جدید قابل برگرداندن مستقیم نباشد. موتور جدید فقط خطاهای جدید را روی گره نگه می‌دارد.
- چند جرنی هم‌زمان می‌توانند کاربران یکسان داشته باشند؛ هش جداگانه هر Flow تعریف می‌شود و آمار نیز جداگانه ثبت می‌شود.
- آمار مراحل شامل انتقال‌های ثبت‌شده است. پس از پاک‌سازی، خروجی CSV جزئیات کاربران خروج‌یافته عمداً خالی می‌شود؛ عددهای تجمیعی در داشبورد باقی می‌مانند.
- دامنه‌های خارجی و API/SMS باید برای جلوگیری از ارسال اشتباه در محیط تست بررسی شوند. تغییرات حداقل با PHP lint بررسی شده‌اند، اما بدون SQL Server واقعی، تست هم‌زمانی و قطعی شبکه قطعی نیست.
- نوع سه جدول جدید در SQL Server: `flow_id BIGINT`, `user_digest VARCHAR(64)`, `node_id VARCHAR(80)`, `arrivals` و شمارنده‌های تجمیعی `BIGINT`, و `created_at/updated_at DATETIME2(3)`. تبدیل در WHERE ستون‌های VARCHAR همچنان در سمت پارامتر انجام می‌شود؛ اگر جداول قدیمی قبلاً با NVARCHAR ساخته شده‌اند، باید تیم DBA آن‌ها را جداگانه ممیزی کند.
